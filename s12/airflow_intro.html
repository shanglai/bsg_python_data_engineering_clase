Automatización básica
Cronjobs:
tareas programadas
en Linux
Un cronjob le dice al sistema operativo: "corre este script todos los días a las 2am" — sin intervención humana.
⏰
¿Cuándo usarlo?
Reportes diarios, backups, sincronización de datos, limpiezas nocturnas. Tareas simples y repetitivas con horario fijo.
✅
Ventajas
Nativo en Linux/Mac. Sin instalar nada. Simple. Funciona desde siempre.
⚠️
Limitaciones
Sin UI, sin logs centralizados, sin reintentos automáticos, sin dependencias entre tareas. Si falla, no siempre te enteras.

──¿Por qué Airflow?──
Cron funciona. Airflow escala.
⏰
Cronjob
Simple
Sin interfaz visual — todo en terminal
Sin reintentos automáticos al fallar
Sin dependencias entre tareas
Los logs se pierden si no los guardas
Si el servidor está apagado, la tarea no corre
Un script por cron — no hay orquestación
✈️
Apache Airflow
Producción
UI web con estado de cada tarea en tiempo real
Reintentos configurables por tarea
Dependencias explícitas entre tareas (DAG)
Logs centralizados, descargables por tarea
Backfill — puede correr días pasados que fallaron
Alertas por email cuando algo falla

El corazón de Airflow
DAG: Directed
Acyclic Graph
Un grafo de tareas donde cada nodo es una tarea y cada flecha es una dependencia. "Si A termina bien, corre B."
health_check
✓ ok
↓
extraer_datos
✓ 80 filas
↓
transformar
⟳ corriendo
↓
cargar_mysql
pendiente
↓
calcular_metricas
pendiente
Conceptos del DAG
DAG
Directed Acyclic Graph
El pipeline completo. Define qué tareas existen, en qué orden y cuándo correr.
Task
Unidad de trabajo
Cada paso del pipeline es una tarea. Puede ser un PythonOperator, HttpSensor, BashOperator, etc.
>>
Dependencia
t1 >> t2 significa "t2 solo corre si t1 terminó exitosamente".
schedule
Frecuencia de ejecución
Sintaxis cron o alias: @daily, @hourly, "0 2 * * *"

Setup · airflow standalone
Levantar Airflow en local
Un solo comando levanta el scheduler, el webserver y la base de datos SQLite de Airflow.
1. Instalar (ya debería estar corriendo)
pip install apache-airflow==2.10.3 # ~2 min
2. Inicializar la base de datos interna
export AIRFLOW_HOME=~/airflow airflow db init
3. Levantar todo con un solo comando
airflow standalone # Esto levanta: # - webserver → localhost:8080 # - scheduler → procesa los DAGs # - SQLite → estado de las tareas
4. Las credenciales aparecen en el output
# Busca esta línea en el terminal: Login with username: admin password: xxxxxxxx # O en: ~/airflow/simple_auth_manager_passwords.json
5. Abrir la UI
http://localhost:8080
📁
Dónde poner los DAGs
Airflow lee los DAGs de ~/airflow/dags/. Copia o crea tus archivos .py ahí. El scheduler los detecta automáticamente en ~30 segundos.
→ mkdir ~/airflow/dags
⚡
Trigger manual desde la UI
En la UI, botón ▶ junto al DAG para correrlo ahora sin esperar el schedule. Útil para testing en clase.
→ DAGs → nombre del DAG → ▶ Trigger DAG
🔴
Ver por qué falló una tarea
Clic en el cuadro de la tarea → Log → ves el traceback completo igual que en tu terminal.
→ Aquí veremos el error de puerto de BD
🛑
Detener Airflow
Ctrl+C en la terminal donde corre airflow standalone. El estado de los DAGs se conserva en SQLite.

⚠️ El twist didáctico
El DAG arranca con un puerto de BD incorrecto. Verán el DAG en rojo, leerán el log del error, lo corregirán y lo volverán a correr. Eso es lo que hace un DE real.
DB_PORT = 9999 ← empieza así, luego lo corrigen a 10031
1
health_check_api
HttpSensor al localhost:8001/health. Si la API no responde, el DAG no avanza.
2
extraer_datos
PythonOperator que llama extraer() y guarda en XCom.
3
transformar_datos
PythonOperator que llama transformar() sobre lo extraído.
4
cargar_mysql ← aquí truena
PythonOperator con puerto 9999 → falla → leen el log → corrigen → rerun.
5
calcular_metricas
PythonOperator que actualiza metricas_sucursal en MySQL.
